# MASL — правила проекта

Telegram Mini App для спонтанных встреч в Москве: лобби-события, карма, бот с временными группами. ТЗ и стадии — в [tech.md](tech.md). Этот файл — жёсткие правила; держите его короче 200 строк.

## Паспорт

- Монорепозиторий pnpm + Turborepo, Node 22, TypeScript ~6.0.
- `apps/api` — NestJS 12 (ESM) на Fastify. Все маршруты под `/api`. Отдаёт и собранный Mini App с того же домена.
- `apps/web` — SvelteKit 3 SPA (adapter-static), Svelte 5 runes, Tailwind 4, `@telegram-apps/sdk`. Алиас `#lib`, не `$lib`.
- `packages/db` — Drizzle ORM + PostgreSQL/PostGIS, миграции в `packages/db/drizzle`.
- `packages/shared` — zod-схемы контрактов API, перечисления, продуктовые константы.
- Деплой: один Docker-образ (`Dockerfile`), свой сервер через `deploy/`, инструкции в `docs/`.

Файлы памяти проекта (читать перед работой, обновлять после задачи):

- [decisions.md](decisions.md) — почему сделано именно так. Не «улучшать» описанное там без нового решения.
- [bugs.md](bugs.md) — известные баги и грабли.
- [todo.md](todo.md) — что в работе сейчас.
- [style.md](style.md) — дизайн-система и стиль кода.

## Команды

```sh
pnpm install
pnpm db:up && pnpm build && pnpm db:migrate && pnpm db:seed   # локальная база в Docker
pnpm dev                                                       # API :3000, web :5173 (проксирует /api)
pnpm format:check
TEST_DATABASE_URL=postgres://masl:masl@localhost:5432/masl pnpm turbo run build typecheck lint test
```

## Жёсткие правила

### Язык и коммиты

1. Комментарии в коде и сообщения коммитов — кратко и на английском. Тексты интерфейса, ошибки для пользователя и сообщения для оператора (логи запуска, ошибки конфигурации) — на русском. Документы для людей (`*.md`, `docs/`) — на русском.
2. Коммиты от имени владельца репозитория, без следов нейросети: никаких `Co-Authored-By`, упоминаний ИИ, ассистентов и сессий в коммитах, коде и комментариях.
3. Один коммит — одно логическое изменение. Сообщение в повелительном наклонении: `Add lobby feed endpoint`.

### Код

4. DRY. Общие типы, константы и схемы живут только в `packages/shared`; не копировать их в `apps/api` или `apps/web`. Повторяющийся код выносить в функцию, а не дублировать.
5. Не выдумывать контракты API. Каждый эндпоинт описан zod-схемами запроса и ответа в `packages/shared/src/schemas.ts`; API валидирует ими вход (`ZodValidationPipe`), веб обращается к API только через `apps/web/src/lib/api.ts`. Нет схемы — сначала схема, потом код.
6. Продуктовые числа (карма, лимиты, окна времени) — только из `packages/shared/src/constants.ts`. Числа, которых нет в ТЗ, не придумывать молча: записать в decisions.md.
7. Не добавлять зависимости без необходимости; сначала проверить, нет ли нужного в уже подключённых.
8. Не оставлять закомментированный код, `console.log` и TODO без записи в todo.md.

### Заморозка ядра

9. Ядро этапов 0–1 менять только если задачу без этого не решить, и тогда записать причину в decisions.md:
   - `apps/api/src/auth/`, `apps/api/src/session/`, `apps/api/src/config/`, `apps/api/src/db/`, `apps/api/src/app.factory.ts`, `apps/api/src/main.ts`, `apps/api/src/spa.ts`, `apps/api/src/common/`;
   - `packages/db/src/client.ts`, `migrate.ts`, `geo.ts`, `bin/`;
   - `apps/web/src/lib/telegram.ts`, `apps/web/src/lib/session.svelte.ts`, `apps/web/src/lib/api.ts` (добавлять функции можно, менять механику запросов и сессии нельзя);
   - `Dockerfile`, `deploy/`, `.github/workflows/`.
10. Применённые миграции не редактировать: только новая миграция. После `pnpm db:generate` проверить SQL (см. bugs.md про `geography`).

### Безопасность

11. Каждый эндпоинт, кроме `/api/health` и `/api/auth/telegram`, закрыт `AuthGuard`. Пользователя брать только из сессии, не из тела запроса.
12. Владение проверять в сервисе на каждом чтении и изменении (IDOR): хост управляет только своими лобби, участник видит только свои заявки. На каждый новый ресурс — e2e-тест «пользователь Б не видит и не меняет данные пользователя А».
13. Точный адрес и координаты лобби отдавать только хосту и одобренным участникам. Публично — только примерное место. Не допускать утечки через расстояния, сортировку, карту и тексты ошибок.
14. Секреты только в `.env` (в git не попадают). Не печатать токены и пароли в логах и ответах. В примерах — заглушки со словом `replace`.
15. SQL только через Drizzle и его шаблон `` sql`...` ``; никакой склейки строк с пользовательским вводом.
16. Лимиты и антиспам проверять на сервере, а не только в интерфейсе.

### Тесты и проверки

17. Перед коммитом: `pnpm format:check` и `pnpm turbo run build typecheck lint test` зелёные. Красное не коммитить.
18. Тесты проверяют реальное поведение: никаких тестов, которые проходят всегда. Логику с базой тестировать на настоящем PostGIS (`TEST_DATABASE_URL`), а не на моках.
19. Баг-фикс начинается с теста, который этот баг воспроизводит.

### Этапы и PR

20. Каждый этап из tech.md — отдельная ветка `stage-N-<name>` от свежего `main` и PR после зелёного CI. Сливает владелец.
21. Перед кодом этапа — план и макеты экранов на утверждение владельцу; код после его «да».
22. В описании PR раздел «Проверить лично»: архитектура, права доступа (видит ли пользователь А данные Б), сценарии злоупотреблений (лимиты, карма, обход порядка шагов).
23. После каждой задачи обновить todo.md, а новые решения и грабли — в decisions.md и bugs.md.
